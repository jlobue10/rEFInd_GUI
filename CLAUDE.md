# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Qt (C++17) GUI for customizing and installing the rEFInd bootloader, aimed especially at dual-boot handhelds (ASUS ROG Ally/Ally X, Legion Go, Steam Deck). It builds for **both Linux and Windows** from the same sources. Linux install targets: Fedora/Nobara/Bazzite (RPM), any pacman-based Arch distro incl. CachyOS (PKGBUILD; SteamOS is explicitly refused — its immutable rootfs belongs to the sibling SteamDeck_rEFInd project), and Debian/Ubuntu (deb); Windows: `windows/install-rEFInd-GUI.ps1` into `%LOCALAPPDATA%\rEFInd_GUI`.

## Build

Everything compiled lives in `GUI/src` (CMake, auto-detects Qt6 then Qt5) and builds three targets: the `espops` static library (all privileged ESP/config/theme/randomizer logic), the `rEFInd_GUI` Widgets app, and `rEFInd_GUI_helper` — a QtCore-only console binary that links `espops` and is what runs privileged on Linux (via sudo) and as the Windows Scheduled Tasks' action. `espops/` and `helper/main.cpp` are **parity-locked byte-identical** with the sibling SteamDeck_rEFInd repo (same workflow as `osdetect_*`): port changes by copying the files and re-applying only `espops/espconstants.h`, the one repo-owned file. Linux:

```
cd GUI/src
mkdir -p build && cd build
cmake ..
make
```

Windows (MSYS2 UCRT64 shell — installed at `C:\msys64` on this machine; launch via `MSYSTEM=UCRT64 C:\msys64\usr\bin\bash.exe -lc "..."`):

```
cmake -G Ninja -S GUI/src -B <builddir>
cmake --build <builddir>
windeployqt6 <builddir>/rEFInd_GUI.exe   # plus MinGW/ICU DLLs for standalone use (ldd the exe)
```

The helper needs `taskschd` on the link line for the Task Scheduler COM CLSID/IIDs — MinGW does **not** carry them in libuuid. A dev build of either exe only runs from a shell with the MSYS2 runtime on `PATH` (`C:\msys64\ucrt64\bin`) plus `QT_PLUGIN_PATH` for the GUI; without those it dies with no window and no error, and a Scheduled Task pointing at it fails with `0xC0000135` (DLL not found).

**This machine's quirk:** Norton AV silently deletes `CMakeCache.txt` for build dirs inside `Documents` — configure into a build dir outside the repo (e.g. the scratchpad). The Windows exe embeds a `requireAdministrator` manifest (`rEFInd_GUI.manifest` via `rEFInd_GUI.rc` for MinGW, link flag for MSVC), so it triggers UAC on launch. Norton also MITMs TLS here; its root CA was exported into MSYS2's trust store (`/etc/pki/ca-trust/source/anchors/norton-root.pem`) — if pacman ever fails with certificate errors again, that's why, and `curl --ssl-no-revoke` is how to confirm a URL works past Norton's revocation break.

### Windows packaging

`windows/assemble-deploy.sh <exe> deploy` gathers the exe + **`rEFInd_GUI_helper.exe`** (it must sit beside the GUI in the build dir; the script hard-fails otherwise) + Qt plugins (windeployqt) + the MinGW/ICU DLL closure (`windows/copydeps.sh`, an `ldd`-based best-effort copy) + `windows/*.ps1` (now only the standalone `install_rEFInd.ps1`/`uninstall_rEFInd.ps1` pair and the manual installer) + `icons/` + `backgrounds/` + `themes/` + a seed `GUI/refind.conf` into `deploy/` — the exact final runtime layout. `windows/rEFInd_GUI.iss` (Inno Setup) packages `deploy/` into a **machine-wide** installer (`PrivilegesRequired=admin`) targeting `%ProgramFiles%\rEFInd_GUI`, so the executables are protected from unprivileged modification; mutable configuration lives in `%LOCALAPPDATA%\rEFInd_GUI` (`Platform::dataDir()`), seeded on first launch by `Platform::prepareDataDir()`. Its `[Run]` step invokes `helper migrate-tasks` so Scheduled Tasks left by an older version stop pointing at removed `.ps1` wrappers, `[InstallDelete]` scrubs those superseded scripts from `{app}\windows` (Inno never deletes files it no longer ships), and `[UninstallRun]` unregisters every task name, current and legacy, with `schtasks`. The installer also scrubs the legacy pre-3.x per-user install (exe/DLLs/scripts in `%LOCALAPPDATA%`, per-user shortcuts, HKCU uninstall key). No portable build is published — outside Program Files the app's privileged binaries would be user-writable. `.github/workflows/windows-release.yml` runs the whole chain on a `v*` tag, and Authenticode-signs the exe, **the helper exe**, the remaining `.ps1` scripts, and the installer via **SignPath Foundation** (free OSS signing) — two-stage: sign `deploy/` contents, then build and sign the installer. Signing is gated on the `SIGNPATH_ORGANIZATION_ID` repo variable, so the workflow still produces unsigned builds until SignPath is configured (`windows/SIGNING.md`). Build artifacts (`deploy/`, `build-*/`, `windows/Output/`) are gitignored.

There is no linter. Tests are opt-in: `cmake -DBUILD_GUI_TESTS=ON` then `ctest --test-dir <builddir>`. Six suites — `loadoption`, `configinstall`, `themesinstall`, and `randomize` cover `espops` and run on **both** platforms (POSIX-only cases `QSKIP` on Windows); `osdetect` and `espresolve` compile Linux-only sources and are gated to Linux. They are the first genuinely unit-testable privileged code in the project and they earn their keep: the Windows overwrite-rename and open-handle bugs above were both caught here rather than on a user's ESP.

**Important:** both `rEFInd_GUI.spec` (`%prep`) and `PKGBUILD` (`build()`) do a fresh `git clone` of this repo from GitHub rather than using the local checkout. Package builds therefore only pick up changes after they are pushed to `main`.

## Releasing / version bumps

The version is duplicated in several places that must be kept in sync:

- `VERSION` (plain text, e.g. `2.0.0`) — fetched at runtime by the "Check For Update" button and compared component-wise (`QVersionNumber`) against `APP_VERSION`
- `GUI/src/mainwindow.cpp`: `static const char APP_VERSION[]` (also feeds the About box text)
- `GUI/src/CMakeLists.txt`: `project(rEFInd_GUI VERSION ...)`
- `GUI/src/rEFInd_GUI.manifest`: `assemblyIdentity version="X.Y.Z.0"` (four-part)
- `windows/rEFInd_GUI.iss`: `#define AppVersion`
- `rEFInd_GUI.spec`: `Version:` (plus a `%changelog` entry)
- `PKGBUILD`: `pkgver`
- `debian/changelog`: new top entry (`refind-gui (X.Y.Z) unstable; ...`)

The helper needs no separate version: `ESPOPS_APP_VERSION` is stamped from `project(VERSION)` at build time and is what `helper --version` prints. That is load-bearing on Linux — the GUI compares it against `APP_VERSION` and refuses to act on a mismatch (the version handshake that replaced the tamper hash), so **the GUI and the helper must be released together**; shipping one without the other gives every user a "reinstall to repair" dialog.

## Architecture

Platform-specific code is confined to three files; everything else is shared. Never build shell command strings from user input — external commands go through `QProcess` with argument lists, file copies through `QFile::copy`.

- **`OSDetector`** (interface in `osdetect.h`): `osdetect_common.cpp` holds the platform-neutral logic. `detect()` iterates **every** ESP in the partition list and scans each reachable one (`espScanRoot(part)` — platform-specific), so multi-ESP machines (Windows ESP on one disk, Linux ESP on another) are fully covered rather than just one "system" ESP. Every discovered entry is tagged with its ESP's **partition GUID** as `volume` (`espVolumeId`), so the generated `menuentry` boots regardless of which ESP rEFInd itself launched from. The per-ESP `EFI/` vendor-dir scan (loader preference shim → GRUB → systemd-boot; `bootmgfw.efi` → Windows, `steamcl.efi` → SteamOS) also renames a bare systemd-boot loader (`/EFI/systemd`) to the running distro when it's on that distro's own ESP (so CachyOS shows "CachyOS", not "systemd-boot"); on any other ESP (e.g. a Linux ESP scanned from Windows, where os-release doesn't exist) it falls back to the `title` lines in that ESP's `loader/entries/*.conf`, mapping any title word onto the known-distro-name table ("Linux Cachyos Deckify" → "CachyOS"). Cross-volume rules in `assembleEntries` cover ESPs that couldn't be scanned (unmounted `SYSTEM`/`SYSTEM_DRV`-labelled Windows ESP → Windows by partition GUID; `BATOCERA`/`VTOYEFI`; removable ESPs by partition GUID). `osdetect_linux.cpp` enumerates via `lsblk -J` — **`NAME` must be in the `-o` column list** or lsblk (≥ 2.42) drops the disk→children tree and emits partitions flat; the parser walks recursively so either shape works. `MOUNTPOINT` is the pre-2.37 util-linux fallback for `MOUNTPOINTS`. It names the running distro from `/etc/os-release` `ID`/`ID_LIKE` (so `/EFI/fedora` shows "Nobara" on Nobara); an ESP mounted at `/boot`, `/boot/efi`, or `/efi` is the running system's. On Linux an ESP is scannable only where already mounted (mounting needs root, which detection avoids). `osdetect_win.cpp` enumerates via one PowerShell `Get-Partition`/`Get-Disk`/`Get-Volume` → JSON call (including each partition's `\\?\Volume{guid}\` access path) and mounts the letterless system ESP with `mountvol <X>: /S`; a letterless **non-system** ESP (e.g. a Linux distro's ESP — the ROG Xbox Ally X dual-boot case) is mounted on a temp *directory* via `mountvol <dir> \\?\Volume{guid}\`, which doesn't consume a drive letter (both unmounted after; `releaseEspRoot` treats any root longer than `"Z:"` as a directory mount point to remove). Without that mount the Windows GUI never saw CachyOS's systemd-boot at all. Windows gotcha: letterless partitions serialize `DriveLetter` as a NUL char, not empty — hence the "is it actually a letter" check.
- **`Platform` namespace** (`platform.h/.cpp`, the only `#ifdef Q_OS_WIN` site): data dir (`~/.local/rEFInd_GUI` vs `%LOCALAPPDATA%\rEFInd_GUI` — same layout below it), installer launches (xterm + .sh vs PowerShell), config/theme installs and randomizer toggles (`sudo -n` the helper + systemd units vs in-process `espops` + Scheduled Tasks registered through the Task Scheduler COM API), firmware_bootnum availability (Linux only; the checkbox is disabled on Windows), Install Source options (Windows has only "Sourceforge"). `installConfig()`/`installThemes()` return an exit code plus captured output, and `MainWindow` shows the success/failure dialog from it — short human-readable messages and distinct exit codes exist for exactly this reason. All Windows launches of PowerShell (here and in `osdetect_win.cpp`) go through `Platform::windowsSystemExecutable()` — absolute `%SystemRoot%\System32\...` paths, never PATH lookup — and every detection PowerShell command carries the load-bearing `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8;` prologue (PS 5.1 emits redirected output in the OEM codepage; a localized volume label once produced invalid-UTF-8 JSON and detection found no OS at all — don't drop it). `prepareDataDir()` seeds `icons/`, `backgrounds/`, and `themes/` into the data dir via `copySeedDir()`: merge-add-new — files introduced by an update appear, existing user files are never overwritten.
- **Unreadable-ESP detection recovery + Deep Scan** (since 2.4.0, ported from the sibling SteamDeck_rEFInd repo — the four `osdetect_*` files are kept **byte-identical** to that repo's except its extra `/esp` mountpoint in `isRunningSystemEsp()`; port detection fixes by copying the files and re-applying that one hunk there, not here). Detection runs unprivileged, and Fedora-family installs mount `/boot/efi` `umask=0077` root:root, so `scanEspRoot()` used to silently see nothing. `detect()` now distinguishes "couldn't look" (`espRootUnreadable()`) and recovers entries from the cache written by `scan_esp.sh` (an opt-in elevated scan behind the Deep Scan button, staged to `~/.local/rEFInd_GUI/scan_esp.sh`, cache at `<dataDir>/GUI/esp_scan.conf` keyed by partition GUID) or, without a cache, from `efibootmgr -v` (world-readable, no password). `classifyLoaderPath()` names recovered entries exactly as a filesystem scan would and mirrors `scanEspRoot()`'s skip list (rEFInd, `/EFI/BOOT`, drivers/tools/memtest, non-`bootmgfw` Microsoft plumbing). The Deep Scan button is disabled via `espDeepScanUseful()` when every conventional ESP mountpoint is readable. **systemd automounts** (since 2.6.1): SteamOS 3.9 mounts `/esp` and `/efi` through `esp.automount`/`efi.automount` — until a path resolves *through* the mount point, the vfat mount doesn't exist, lsblk shows the partition unmounted, and detection skipped the ESP entirely (only label-matched media like Ventoy survived; Deep Scan reported "No ESP found"). Three layers fix this: `listPartitions()` and `espDeepScanUseful()` stat `<point>/.` for `/esp`, `/efi`, `/boot/efi`, `/boot` to trigger the automounts (a plain `stat()` of the mount point does NOT trigger — `AT_NO_AUTOMOUNT` since Linux 4.14; the trailing `/.` forces traversal, which triggers regardless of the root-only permission on the mounted fs); `detect()` recovers entries for a *completely unmounted* ESP from the deep-scan cache / `efibootmgr` by partition GUID (previously only mounted-but-unreadable ESPs got recovery); and `scan_esp.sh` passes unmounted ESPs to its root payload as device paths, which temp-mounts them read-only for the scan. Also beware findmnt on automounted paths: it lists the `autofs` row (SOURCE `systemd-1`) **before** the real vfat row, so `findmnt -no SOURCE <mp> | head -1` returns `systemd-1` — the scripts use `grep -m1 '^/dev/'` for SOURCE and `tail -1` for FSTYPE instead; `findmnt -S <dev>` is immune (autofs rows have a different source device).
- **`MainWindow`** (`mainwindow.cpp`, platform-free): detection results feed the four Boot Option combos (`BootEntry` payloads via `QVariant`), refreshed by the Rescan button. `on_Create_Config_clicked` → `createBootStanza` writes `<dataDir>/GUI/refind.conf`, one data-driven stanza per non-None slot; the optional "Include all OSes" checkbox (`IncludeExtraEntries` in the INI, off by default) appends stanzas for every *detected* entry not already slotted — after the slotted ones, with stock rEFInd icons (`stockIconFor`) — for outlier machines with more valid bootloaders than slots; `default_selection` is the chosen entry's position among generated stanzas. Legion Go (DMI/CIM board `LNVNB161216`) forces `resolution 2560 1600`; Legion Go 2 (DMI product name `83N0`/`83N1` — same board name as the Go 1, so it's checked first) forces `resolution 1920 1200`; ROG Xbox Ally / Ally X (DMI/CIM board prefix `RC73YA`/`RC73XA`) forces `resolution 1920 1080` (the numbered `resolution 3` picks the wrong mode there). Devices with no quirk get `resolution <W> <H>` from `OSDetector::nativePanelResolution()` — the built-in panel's EDID/DRM preferred mode, internal display (eDP/LVDS/DSI, or WMI `VideoOutputTechnology` INTERNAL/eDP/LVDS on Windows) preferred over external outputs so a docked handheld reports its own screen; Linux reads the first line of `/sys/class/drm/card*-*/modes`, Windows parses the EDID preferred-timing DTD via `WmiGetMonitorRawEEdidV1Block`. Note it returns the mode **as the panel reports it** (portrait on portrait-native panels — that's what the Legion Go quirks exist to override). Only when nothing is detected does the config fall back to `resolution 3`. That whole quirk→EDID chain lives in `effectivePanelResolution()`. **Res Override**: a checkbox + width/height boxes (main grid row 10) let the user force `resolution <W> <H>`; when armed with two positive values (`resolutionOverride()`), it beats the quirks too — it exists to escape a wrong automatic choice — and it is never active unless the user checked the box. Stored in the INI as `[Resolution]` `ResOverrideEnabled`/`ResOverrideWidth`/`ResOverrideHeight`; the boxes are seeded once (only when the INI holds nothing) from `effectivePanelResolution()`, which `startDetection()` computes on the detection worker thread (`panelPrefill`) because the quirk probes and EDID read each spawn PowerShell on Windows. Selected PNGs are copied to canonical names (`background.png`, `os_icon1..4.png`). All Create-Config writes are staged (`QSaveFile` with `setDirectWriteFallback(false)`, plus an explicit short-write check → "the disk may be full"); if any selected image can't be staged, the previous `refind.conf` is kept — never publish a config whose assets didn't land. The firmware_bootnum lookup (`steamFirmwareBootNum()`) matches the SteamOS entry by its immutable loader device path (`HD(...)/\EFI\steamos\steamcl.efi`) with exact label `SteamOS` only as a fallback and first-in-BootOrder as the tiebreaker — not the old `.*steam` label substring.
- **rEFInd install scripts, efibootmgr phase** (`refind_install_Sourceforge.sh`, `refind_install_package_mgr.sh`): the installer-created "rEFInd Boot Manager" entry (exact label) is deleted first, then the new `rEFInd` NVRAM entry is created **before** any plain old rEFInd entries are deleted — the old delete-then-create order left machines with *no* rEFInd entry whenever the create failed (observed live: `lsblk -no PKNAME` returned empty under util-linux 2.42, producing `efibootmgr -c -d /dev/ ...`). Disk resolution falls back to sysfs (`/sys/class/block/<part>` parent dir) when PKNAME is empty and validates `-b "$ESP_DISK"` before touching NVRAM. The new entry is identified as the head of BootOrder (which `efibootmgr -c` sets) so cleanup can't delete it. efibootmgr ≥ 18 appends a tab + device path after the label even without `-v`, so every label regex must end `(\t.*)?$` rather than anchoring at the label — `$`-anchored label matches silently never match (observed live: neither the "rEFInd Boot Manager" pre-delete nor the new-entry check matched, leaving two rEFInd entries). Both scripts end with a verification summary read back from live NVRAM (entry exists + first in BootOrder) and keep their xterm open (`read` prompt, tty-guarded) so status is visible; the package-mgr script must keep zenity's stdout protocol clean — diagnostics go to stderr. After the efibootmgr phase, both scripts run `sudo sbctl-batch-sign` when the OS is CachyOS (`/etc/os-release` `ID=cachyos`) **and** Secure Boot is enabled (SecureBoot efivar's fifth byte = 1, dependency-free `od` read) — CachyOS enforces sbctl-signed binaries under Secure Boot, so unsigned rEFInd files would be refused by the firmware; missing tool or a failed sign warns and continues. `windows/install_rEFInd.ps1` mirrors the applicable parts: it writes a dedicated `rEFInd` **Boot#### EFI variable directly** (`SetFirmwareEnvironmentVariableW` + `SeSystemEnvironmentPrivilege`, byte-identical to what `efibootmgr -c` produces — the EFI_LOAD_OPTION builder was validated byte-for-byte against a live efibootmgr-created entry) and prepends it to `BootOrder`. It must NOT repoint `{bootmgr}` as versions ≤2.2.0 did: the Windows Boot Manager entry carries a `WINDOWS...BCDOBJECT={...}` optional-data blob that trails the loader path in `efibootmgr -v` ("malformed entry", issue #23) and reaches rEFInd as junk load options — the installer now restores a repointed `{bootmgr}` when it finds one (migration). bcdedit **cannot** create firmware entries on current Windows 11 (`/application firmware` was removed; adding a non-firmware object to `{fwbootmgr} displayorder` reports success but is silently ignored), hence the direct NVRAM write. Entries carrying the `"WINDOWS"` blob (hex `57494e444f5753`) are never overwritten/deleted — that's `{bootmgr}`'s own variable. `bcdedit` (via the exit-code-checked `Invoke-Bcdedit` wrapper — a native exe whose failures don't trip `$ErrorActionPreference='Stop'`, and stderr under `2>&1` becomes a terminating NativeCommandError) is still used for `{bootmgr}` migration/snapshot; state is backed up before modification and the script ends with a read-back SUCCESS/WARNING/FAILED summary from live NVRAM. Progress is shown as numbered colored step banners (`Write-Step`, 6 steps) plus a `Write-Progress` bar, with the summary verdict colorized. If Secure Boot is enabled (`Confirm-SecureBootUEFI`, try/catch = "not enabled"), a yellow note explains that sbctl-managed distros (CachyOS) must sign the new binaries from Linux — **rEFInd_GUI only; the SteamDeck_rEFInd copy of this script deliberately omits the Secure Boot block**, and is otherwise identical modulo the `rEFInd_GUI`→`SteamDeck_rEFInd` data-dir substitution. The script ends with a tty-style `Read-Host` pause then `[Environment]::Exit`, which closes the window even under the launcher's `-NoExit` (no stray prompt). `windows/uninstall_rEFInd.ps1` reverses everything (restore `{bootmgr}` if repointed, delete rEFInd Boot#### entries **whose HD node matches the system ESP GUID** — rEFInd entries on other ESPs, i.e. Linux-side installs, are reported and left alone — remove `EFI\refind`/`EFI\Xbox360`, unregister the randomizer task; `-KeepEspFiles` keeps files); the Inno uninstaller runs it elevated via `[UninstallRun]`+`Verb: runas` after a yes/no prompt (`InitializeUninstall`), and `[UninstallDelete]` scrubs the whole per-user app dir. The UEFI NVRAM helper block is duplicated between install and uninstall scripts — keep in sync. Both Linux installers fail closed through `fail_install()`: the `BOOT_CHANGES_STARTED` sentinel is set right before `refind-install` runs so the failure summary can distinguish "nothing was changed" from "Windows and unverified fallback entries were left active"; the ESP's PARTUUID is validated *before* any boot entry is created (an MBR/PARTUUID-less ESP aborts with an explanation instead of creating an unverifiable entry), and a failed package-DB refresh falls back to an already-installed `refind-install` rather than aborting. `windows/install_rEFInd.ps1` stages its downloads in `%SystemRoot%\Temp\rEFInd_GUI-Staging-<guid>` with an admin-only DACL applied via `Set-Acl` (works under both PS 5.1 and pwsh; `C:\ProgramData` was squattable through Users create-subfolder + CREATOR OWNER), refuses a pre-existing GUID dir or reparse point, sanity-checks downloads by magic bytes (`Test-FileSignature` — deliberately *not* Authenticode; rEFInd binaries are unsigned), and publishes via `Publish-FileAtomically` (staged same-directory swap — `Move-Item -Force` is delete-then-move, not `ReplaceFile`, so the window is short, not zero).
- **Privileged actions and the helper binary** (`GUI/src/helper/` + `GUI/src/espops/`, since the native-helper consolidation — `NATIVE_HELPER_DESIGN.md` is the authoritative design). All privileged config/theme/randomizer work is compiled code in the `espops` static library, which links into both the GUI and a small QtCore-only console binary, `rEFInd_GUI_helper`. `espops/` **and** `helper/main.cpp` are parity-locked byte-identical with the sibling SteamDeck_rEFInd repo; `espops/espconstants.h` is the single repo-owned file (product/data-dir names, the `/etc` helper path, the Windows task table). Subcommands: `install-config`, `install-themes`, `randomize-background`, `randomize-theme`, and on Windows `bootnext`, `migrate-tasks`, `enable-logon-task`/`disable-logon-task <subcommand>`. Exit codes are a contract the GUI keys its dialogs off: 0 success, 2 no/invalid invoking user, 3 no rEFInd ESP, 4 read-only target, 5 staging/space, 6 no source config / no themes, 64 usage; the randomizers deliberately exit 0 on content/environment problems (a red failed unit for a missing background is worse than the symptom).
  - **Linux** keeps the privilege boundary — the GUI runs unprivileged, so `install-rEFInd-GUI.sh` installs the helper root-owned 0755 at `/etc/rEFInd/rEFInd_GUI_helper` and the sudoers drop-in (`zz_install_config_from_GUI` → `/etc/sudoers.d/zz_install_config_from_GUI`, root-owned 0440, visudo-gated) whitelists the two **exact argument vectors** `… install-config` and `… install-themes`. The `zz_` prefix is still load-bearing — sudo applies the last matching entry in lexical sudoers.d order, so a passworded catch-all drop-in like SteamOS's `wheel` would override a file sorting before it — and the installer removes the old-name rules from previous versions. The systemd randomizer units `ExecStart` the helper's `randomize-*` subcommands. The zenity password fallback is gone: Install Config is passwordless-only, and a missing rule/helper produces a "reinstall rEFInd_GUI to repair" dialog.
  - **The SHA-256 tamper hash-check is gone** along with `matchesShippedScript()`, both `*ScriptTrusted()` functions, and the script embeds in `resources.qrc`. Its real job — catching skew between the binary and the `/etc` copies — is now a **version handshake**: the GUI runs `helper --version` (world-executable, no sudo) and compares against `APP_VERSION`, and a mismatch shows the same reinstall dialog. That is skew detection, *not* a security boundary; the boundary is root ownership of `/etc/rEFInd/rEFInd_GUI_helper`, exactly as it was for the scripts. The practical consequence is inverted from before: editing privileged logic no longer risks blocking every user's Install Config, but it *does* mean the helper and the GUI must ship together.
  - **Windows**: the GUI already runs elevated (requireAdministrator manifest), so Install Config / Install Themes call `espops` **in-process** — no PowerShell, no `trustedScriptPath()` location check, no OEM-codepage capture pitfalls. The helper exe ships beside the GUI under Program Files purely so the Scheduled Tasks have something to run when the GUI isn't up, and is Authenticode-signed like the GUI. `install_rEFInd.ps1` and `uninstall_rEFInd.ps1` are the only remaining `.ps1` files (standalone terminal tooling, not sudo-gated GUI helpers); `install_rEFInd.ps1` writes a dedicated `rEFInd` Boot#### firmware entry directly into NVRAM (backup + revert instructions printed) — never run it casually on a dev machine.
- **Config install targets rEFInd's real ESP**, not just the conventionally-mounted one — critical on multi-ESP machines where rEFInd lives on the Windows ESP while the running distro mounts its own ESP at `/boot`. This is now **one** implementation for both platforms (`espops/espresolve_*.cpp` + the shared `espops/loadoption.cpp` parser), replacing the old bash/PowerShell pair that had to be kept in behavioral parity by hand. `EspResolver::resolve()` walks BootOrder-ordered `Boot####` entries first and then the conventional `Boot0000`–`Boot00FF` range (so an entry dropped from BootOrder is still found), preferring a `\EFI\refind\refind*.efi` loader-path match over an exact `rEFInd` label, and **verifies the chosen ESP actually contains `EFI/refind/refind*.efi`** so a stale NVRAM entry can't shadow the live install; then any ESP containing rEFInd; then the running system's ESP. That stale-shadow case is real — observed on the ROG Xbox Ally X, where config went to the Windows ESP while the NVRAM rEFInd entry booted the CachyOS ESP. Variable reads are `/sys/firmware/efi/efivars` on Linux (skip the 4-byte attributes prefix) and `GetFirmwareEnvironmentVariableW` on Windows (locale-independent, unlike the `bcdedit /enum firmware` text parsing it replaced — that silently matched nothing on localized Windows, and it needs `SeSystemEnvironmentPrivilege` enabled first or every read returns empty). The resolver **owns its probe mounts**: unmounted candidates are mounted `ro,nosuid,nodev,noexec` on a private temp dir and unmounted by the destructor, only the chosen target is remounted rw, and only if it was our own probe mount — so keep the resolver alive until all writes are finished and synced. On Windows a letterless ESP is mounted on a temp *directory* (`mountvol`, no drive letter consumed); that mount point is an implementation detail, so `platform.cpp` substitutes the ESP's identity into user-facing messages rather than showing a `…\Temp\espops-XXXXXX\…` path that no longer exists by the time the dialog is read. The whole set (`refind.conf`, `background.png`, `os_icon1..4.png`, `themes/active_theme.conf`) publishes as a staged transaction: every file lands as `.<name>.new.<suffix>` in its destination dir, a stale-staging sweep runs right after the destination is ensured (traps can't survive SIGKILL/power loss), assets publish before `refind.conf`, and a `refind.conf.prev` backup is kept. Staged publish-last, **not** atomic — FAT32 gives no rename atomicity. Publishing goes through `EspOps::publishRename` (in `userio.cpp`), which is `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` on Windows because both `QFile::rename` and UCRT's `std::rename` refuse to overwrite there; note also that `QTemporaryFile` holds its native handle open after `close()`, and Windows cannot rename an open file — destruct the staging object before publishing.
- **Settings persistence**: `QSettings` INI at `<dataDir>/GUI/rEFInd_GUI.ini`. Everything except the boot-option selections restores in the constructor (`readEarlySettings()`) and persists the moment the user changes a control (`initSettingsPersistence()`) — the destructor's `writeSettings()` is only a final snapshot, because force-termination (Xbox overlay / task switcher, suspend on handhelds) skips destructors. Boot-option selections restore in `readSettings()` once the scan delivers combo contents, and persist on change only after that (`settingsLoaded` gates both the exit snapshot and per-change writes; `populating` masks programmatic rebuilds). Selections are stored by *text* (`BootOption0XText`), not index — combo contents are dynamic.

## Themes and the boot-screen preview

- **Bundled themes** (`themes/`, since 3.2.0): seven upstream rEFInd themes (BlackCatMuzzle, Matrix-rEFInd, Starwars-rEFInd, rEFInd-fallout, rEFInd-glassy, rEFInd-mountain, wave, ~11 MB total), each normalized so its directory name is exactly the name its own `theme.conf` references — theme.conf asset paths resolve relative to rEFInd's dir on the ESP, so **don't rename the theme dirs**. Upstream LICENSE/README/preview files are kept for attribution (credits table + takedown note in `README.md`; three themes have no published license). Raw upstream clones (`themes/*-main/`, `themes/*-master/`) are gitignored working material — the normalized copies are the shipped ones (3.2.1 briefly committed the clones by accident).
- **Theme selection**: `Theme_comboBox` (main grid row 13, above the Language row) offers None (empty item data), one entry per `<dataDir>/themes/<name>/theme.conf` (dir name = display text = item data, **never translated** — like BootEntry names), and Random (item data `__random__`, only present when themes exist). Persisted as `[ComboBoxes] Theme` = item data. `populateThemeCombo()` re-runs on `LanguageChange` so `tr("None")`/`tr("Random")` retranslate; the selection survives because it's keyed by data, not text.
- **Config generation**: a non-None selection makes `generateConfigText()` append `include themes/active_theme.conf` as the final directive — the include target never varies, switching themes replaces one file. rEFInd applies the last occurrence of a setting, so the theme deliberately supersedes the generated `banner`/`big_icon_size`/`resolution` above it (`hideui` ORs across files — a theme can only hide *more*), and rEFInd ignores a missing include, so the config stays bootable before Install Themes has ever run. Per-stanza `icon` lines still point at the user-picked `os_iconN.png` — a theme's `icons_dir` doesn't override explicit icon paths. `stageActiveThemeConf()` resolves Random to a concrete theme at Create-Config time and copies its theme.conf → `<dataDir>/GUI/active_theme.conf`; None removes the staged copy (so Install Config stops publishing a stale one), and a staging failure aborts Create Config just like a failed PNG copy.
- **Two paths to the ESP**: the theme *trees* go to `EFI/refind/themes/<name>/` via the **Install Themes** button — Linux runs `sudo -n /etc/rEFInd/rEFInd_GUI_helper install-themes` (the second exact-argument NOPASSWD line in `zz_install_config_from_GUI`), Windows calls the same `espops/themesinstall.cpp` in-process from the already-elevated GUI. Shared behavior: free-space precheck, per-theme staged directory swap with `.old-` rollback, distinct exit codes, and the same NVRAM-first ESP resolution as the config install. On Linux root still never reads under the user's home — `espops/userio_linux.cpp`'s `ForkUserFiles` forks, drops to `SUDO_USER` (setgroups → setgid → setuid, in that order), and streams the files from the child, the fd-handoff equivalent of the old `runuser -u … tar` pipe, keeping its guarantees: symlinks refused (vfat can't hold them anyway), no `..`/absolute members, no extraction escape. The three rEFInd installers also copy the themes onto the ESP best-effort at install time (warn-and-continue, never fails the install). The *active* `themes/active_theme.conf` is published by **Install Config** along with the config/PNG set.
- **Theme randomizer** (`helper randomize-theme`, driven by `rEFInd_theme_randomizer.service` on Linux and the at-logon Scheduled Task `rEFInd_GUI_theme_randomizer` on Windows; toggled via `Platform::setThemeRandomizer()` → the shared `setRandomizerUnit()` xterm helper on Linux, `EspOps::setLogonTask()` COM registration on Windows): on each boot copies a random *installed* theme's theme.conf over the ESP's `themes/active_theme.conf`, picking only from the ESP's own root-owned tree — deliberately **no user-writable input** (unlike the bg randomizer there is no `USER`/`HOME` sed placeholder in it), with an anti-repeat compare against the current file. It only changes which theme an already theme-enabled `refind.conf` includes; a Theme=None config has no include line and is unaffected.
- **Boot-screen preview** (`PreviewDialog`, `GUI/src/previewdialog.cpp/.h`, since 3.0.0): the Preview button renders a mock 1280x800 boot screen (rEFInd's reference geometry — background fillscreen, one centered row of entry icons sized/spaced like rEFInd's, selection backdrop behind the default entry, rounded name-initial tiles for missing icons) plus a second tab with the generated `refind.conf` text (tab title deliberately untranslated — it's a filename). `PreviewTheme` (kept **byte-identical to the sibling SteamDeck_rEFInd repo's**) is the only theme.conf parser in the codebase: it reads exactly `banner`, `selection_big`, `big_icon_size`, and `hideui` (only the `label` token; `hideui` accumulates across repeated lines like rEFInd's own config.c, and `label` suppresses the mock's entry names). `resolveThemeAsset()` re-roots any `themes/...` path onto the local themes dir and returns nothing for a dangling path, falling back to the themeless drawing for that element. Random previews a concrete random pick, with a note that Create Config re-picks.
- **Packaging**: `install-rEFInd-GUI.sh` copies `themes/` to `~/.local/rEFInd_GUI/` (plus a `GUI/themes` → `../themes` symlink next to the existing backgrounds one) and installs the root-owned helper binary into `/etc/rEFInd/` (which is what both randomizer units and both sudo-gated actions now run); the RPM spec, PKGBUILD, and `debian/rules` all install `rEFInd_theme_randomizer.service`; `windows/assemble-deploy.sh` ships `themes/` in `deploy/` so `Platform::prepareDataDir()` can seed `%LOCALAPPDATA%`; both uninstallers disable both randomizer units/tasks (the ESP's theme files need no extra handling — they fall with `EFI/refind`).

## Internationalization (GUI)

The GUI is translated via Qt Linguist files: `GUI/src/rEFInd_GUI_{en_US,ar,bn,de,es,fa,fr,hi,id,it,ja,ko,pt,ru,scn,tr,uk,ur,vi,zh_CN}.ts`, listed in `TS_FILES` in `CMakeLists.txt`. On Qt 6, `qt_add_translations()` compiles them at build time and embeds the `.qm` under `:/i18n`, where `main.cpp` loads them with the locale-fallback `QTranslator::load(QLocale(), ...)` overload (plus a `qtbase` translator for Qt's own dialog strings); on Qt 5 the `.qm` are only generated into `translations/` next to the binary. Rules: wrap every new user-facing GUI string in `tr()` (in `Platform`, use `QCoreApplication::translate("Platform", ...)`); after changing strings, refresh **all** `.ts` files with `lupdate` (or the `update_translations` target) so translators see the new entries — unfinished entries just fall back to English. Do NOT translate `BootEntry` display/menu names ("Windows", "SteamOS", "Ventoy", ...): they are matching identifiers persisted by text and produced by the parity-locked `osdetect_*` files. `.ui` strings that are overwritten at runtime are marked `notr="true"` — keep doing that for new ones. The en_US file is the source-language reference and stays untranslated. The `QT_LAYOUT_DIRECTION` message (anchored in `main.cpp`) must stay `RTL` in the ar/fa/ur files — it is what mirrors the layout for right-to-left languages. The remaining shell/PowerShell scripts and the helper binary's output are deliberately English-only (the helper's messages are shown verbatim in GUI dialogs; `espops` is parity-locked, so localizing it is a both-repos change) — see `I18N_AUDIT.md` before localizing them. Now that the tamper hash is gone, `tr()` in `espops` plus `.qm` lookup in the helper is a viable follow-up. Runtime language selection lives in `uitranslation.cpp` (`UiTranslation::apply`, saved as `Language/UiLanguage` in the INI; the Language combo switches live via `changeEvent`/`retranslateUi` + `applyDynamicTexts()` — put any new code-set string in `applyDynamicTexts()` so a language switch refreshes it). Qt 6 builds also embed the matching `qtbase_*.qm` from the build machine under `:/i18n_qtbase` (SteamOS ships no qt6-translations package); `UiTranslation` falls back to them last. Detection runs on a worker thread (`startDetection()`; don't call `detector.detect()` on the GUI thread) and the update check uses `QNetworkAccessManager` (Qt Network) — both UI freezes were deliberate removals; don't reintroduce synchronous variants. The GUI appends diagnostics to `<dataDir>/GUI/logs/` (English on purpose), and boot selections persist by stable key (`BootOption0XKey` = volume|loaderPath) with the old text keys as fallback. Unit tests live in `GUI/src/tests/` and link the parity-locked sources untouched — see the Build section.

## Install-time file layout (context for editing the shell scripts)

`install-rEFInd-GUI.sh` is the user-facing entry point (curl | sh). It copies `GUI/`, `icons/`, `backgrounds/`, and the install/uninstall scripts to `~/.local/rEFInd_GUI/`, builds/installs the RPM (or rpm-ostree layers a release RPM on Bazzite, or `makepkg -si` on CachyOS), and installs root-owned pieces to `/etc/rEFInd/` (the built GUI binary, the `rEFInd_GUI_helper` binary that the sudoers rules and both systemd units point at, and `background-dir` — a plain pointer file naming the user's backgrounds directory, read as *data* by the bg randomizer and never sourced, which is what replaced sed-ing `HOME` into a script).

`uninstall_rEFInd.sh` (repo root, run via sudo) is the Linux counterpart of `windows/uninstall_rEFInd.ps1` — keep their behavior in parity: delete the rEFInd boot entries whose partition GUID matches this distro's ESP (loader-path match covers both the `rEFInd` and refind-install's `rEFInd Boot Manager` labels; entries on other ESPs — a Windows-side install — are reported and left alone), re-activate the Windows boot entry that `refind_install_*.sh` deactivated with `efibootmgr -A`, remove `EFI/refind`, `EFI/Xbox360`, and `/boot/refind_linux.conf` (`--keep-esp-files` skips), disable both randomizer services (bg + theme; the Windows uninstaller likewise unregisters all randomizer Scheduled Task names, old and new), and with `--remove-app` also remove the package (dnf/pacman/apt/rpm-ostree), `~/.local/rEFInd_GUI`, `/etc/rEFInd`, the sudoers rule, and desktop entries. It resolves the invoking user's home via `SUDO_USER` (under sudo, `$HOME` is root's).

The literal tokens `USER` and `HOME` inside `zz_install_config_from_GUI` and `rEFInd_GUI.desktop` are placeholders replaced by `sed` during installation — don't "fix" them to `$USER`/`$HOME`. These are the only two left: the helper binary resolves the invoking user from `SUDO_USER` at runtime, so no privileged executable carries a substituted path any more.

**Xbox 360 controller driver**: all three rEFInd install scripts (`refind_install_Sourceforge.sh`, `refind_install_package_mgr.sh`, `windows/install_rEFInd.ps1`) download `UsbXbox360Dxe.efi` into the ESP's `EFI/refind/drivers_x64/` so gamepads work in the boot menu. The URL currently points at the **jlobue10 fork** of the SkorionOS driver (adds Legion Go 2 PIDs + Ally poll-timeout fix + v1.7.3's right-stick-in-Mouse-mode fix, confirmed on a Legion Go 2 in issue #23); switch it back to SkorionOS in all three scripts once upstream PR #7 — which supersedes the old PIDs-only PR #6 and carries the full fork state — is merged and released upstream. The scripts fetch the standard release `UsbXbox360Dxe.efi` — that's the correct default; `UsbXbox360Dxe-debug.efi` (ESP file logging) is for troubleshooting only. The URL is version-agnostic (`.../releases/latest/download/UsbXbox360Dxe.efi`) so no version needs syncing; only the `.efi` is copied (the driver self-creates `\EFI\Xbox360\config.ini` on first boot). Download failure is non-fatal — it warns and continues. The package-manager script is the one that must `mkdir -p .../drivers_x64` first, since `refind-install` doesn't populate it. Keep this step in sync across all three scripts when editing.

**Touchscreen driver** (since 2.3.6, generalized from AllyTouchI2cDxe): the same three scripts also download [`TouchI2cDxe.efi`](https://github.com/jlobue10/TouchI2cDxe) into `drivers_x64/`, but **only on devices with a supported HID-over-I2C touch panel** — ROG Xbox Ally / Ally X (DMI board_name prefix `RC73XA`/`RC73YA` on Linux, `Win32_BaseBoard.Product` on Windows — same board convention the GUI's resolution quirk uses), Steam Deck OLED/LCD (DMI product_name `Galileo`/`Jupiter` on Linux, `Win32_ComputerSystemProduct.Name` on Windows; LCD supported since driver v1.2.0) and ASUS Zenbook Pro 14 Duo (board_name prefix `UX8402VV`; ELAN9008 on Intel Serial IO — the driver's first Intel platform, supported since driver v1.3.0). These touchscreens are HID-over-I2C (Novatek on the Ally, FocalTech FTS3528 on both Decks — I2C-identical on the two models, differing only in the panel reset GPIO, which the driver resolves itself via SMBIOS), invisible to the USB driver; TouchI2cDxe produces `EFI_ABSOLUTE_POINTER_PROTOCOL`, which rEFInd consumes natively (confirmed working on an Xbox Ally X as AllyTouchI2cDxe v1.0.0; the rename to TouchI2cDxe added the Deck profiles). A successful download also deletes a stale `AllyTouchI2cDxe.efi` from `drivers_x64/` — the old driver would otherwise load as a second AbsolutePointer producer for the same panel. Same rules as the controller driver: version-agnostic `releases/latest` URL, download failure warns and continues (and keeps any old AllyTouchI2cDxe.efi), no config file needed, removed with `EFI/refind` on uninstall, auto-signed by the CachyOS `sbctl-batch-sign` step (`sbctl verify` scans the whole ESP). In `install_rEFInd.ps1` the extra download is a numbered `Write-Step`, so `$TotalSteps` is 7 on a touch device and 6 elsewhere — keep that arithmetic in mind when adding steps. Keep all three scripts in sync.

`rEFInd_bg_randomizer.service` (`ExecStart` = `/etc/rEFInd/rEFInd_GUI_helper randomize-background`) implements the optional random-background-on-boot feature, toggled from the GUI via `systemctl enable/disable` (the shared `Platform::setRandomizerUnit()` helper; the theme randomizer counterpart is covered in the Themes section above). It reads the user's backgrounds directory from the root-owned `/etc/rEFInd/background-dir` pointer and the images themselves in the invoking user's context, so nothing user-writable is ever executed or sourced by root.
